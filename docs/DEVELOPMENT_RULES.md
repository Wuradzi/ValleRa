# Правила обліку змін Raven

Публічна частина правил ведення журналу розробки. Сам журнал
(`docs/DEVELOPMENT_LOG.md`), реєстр доказів (`docs/EVIDENCE_REGISTER.md`),
маніфест `docs/evidence/manifest.json` і навігатор `docs/README.md` зберігаються
лише в локальній копії автора: у чистому клоні їх немає, і це очікувано.

## Шаблон запису журналу

Після завершеної зміни або експерименту додавати **новий** запис у
`DEVELOPMENT_LOG.md`, а не переписувати попередню невдачу як успіх.

```text
ID / дата події / дата запису:
Походження: артефакт / датований звіт / відновлено з листування.
Проблема та очікуваний результат:
Розглянуті варіанти й мотив вибору:
Що змінено (файли, налаштування; без секретів):
Як перевірено (команда, обладнання, корпус, параметри):
Фактичний результат і статус:
Докази (ID реєстру, шлях, за можливості commit):
Обмеження, невдалі спроби, наступний крок:
```

## Правила

- Для нового доказу додавати окремий ID і SHA-256; старі записи не перехешовувати
  мовчки після зміни файлів.
- Команди відтворення завжди наводити через `tester.py`.
- Для документаційних змін достатньо перевірки посилань і маніфесту; не оголошувати
  старий прогін тестів новим.
- Живі перевірки не запускати лише заради заповнення журналу.
- Розрізняти підставні тести, синтетичне аудіо, живий API й користувацьку сесію.
- Не копіювати в журнал секрети, ключі чи приватні діалоги.

Якщо локального журналу немає (чистий клон), не створювати фіктивних записів
і не відновлювати історію з пам'яті: повідомити автору, що журнал відсутній.
