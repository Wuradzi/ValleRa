# ValleRa Voice Assistant

ValleRa — модульний локальний українськомовний голосовий асистент для Windows. Він керує програмами, вікнами, файлами, пам’яттю, нотатками й нагадуваннями. LLM розрізняє розмову та підтримуване прохання без префікса; локальний виконавець перевіряє дію й запитує підтвердження. «Команда: …» залишається явним резервним форматом.

## Стан проєкту

Публічна копія не містить приватних журналів, записів голосу, ключів та
особистих налаштувань. Частина дослідницьких посилань доступна лише в локальній
копії автора. Правила комітів: [безпечна публікація](docs/PUBLICATION.md).

Це стартовий MVP-каркас для дипломної роботи. Він містить робочу архітектуру й базові реалізації, але потребує тестування на цільовому Windows-комп’ютері та поступового доповнення команд.

## Реалізовано

- безперервний покроковий голосовий діалог без слова активації;
- гібридний локальний STT: Vosk визначає межі репліки,
  faster-whisper уточнює повний український текст;
- звичайне спілкування через LLM як основний режим;
- обмежені агентні дії без префікса з перевіркою й підтвердженням; інші точні команди — через «Команда»;
- локальний TTS через Windows SAPI/RHVoice;
- поступова відповідь Gemini й озвучення фразами; постійний Windows TTS-процес;
- WAV-кеш для вибраного аудіопристрою або резервного TTS;
- текстове введення паралельно з голосом;
- команда «Команда: замовкни»;
- реальна самодіагностика STT, TTS, аудіопристроїв, сховища й LLM API;
- Gemini → Groq → OpenAI → Anthropic → Ollama → шаблонний режим;
- до трьох спроб при тимчасових мережевих помилках LLM;
- загальний 90-секундний дедлайн одного LLM-запиту;
- історія 50 повідомлень і резюме старої частини;
- релевантна пам’ять у контексті LLM;
- зашифровані секрети з майстер-паролем і ключем відновлення;
- буфер обміну для паролів з очищенням через 30 секунд;
- нотатки;
- нагадування;
- програми й псевдоніми;
- вікна й процеси;
- пошук файлів та видалення в кошик;
- медіаклавіші;
- DDGS і wttr.in;
- атомарний JSON і п’ять резервних копій;
- логи й JSONL-метрики;
- діагностика;
- перевірка нового GitHub-релізу;
- кросплатформний режим авторизованого аудиту «Душогуб»;
- локальний аудит дозволу, цілей і результатів пентест-сканування;
- ізоляція помилок і тайм-аути модульних навичок;
- модульне додавання навичок.

## Локальний вебінтерфейс

Запуск із кореня проєкту, у підготовленому Python-середовищі:

```powershell
.venv\Scripts\python.exe main.py --web-ui
```

Після введення майстер-пароля **в терміналі** відкриється браузер: темний
інтерфейс із мінімалістичним SVG-образом без напису, діалогом поточної сесії,
  поступовими відповідями фразами, джерелами та підтвердженнями операцій.
Це векторне відтворення погодженого ескізу, не важка 3D-сцена.
Додаткових Python/npm-залежностей, зовнішніх шрифтів чи CDN немає.
Композиція за прототипом користувача: темне обличчя над верхнім краєм
димчастої панелі, статус і три круглі кнопки — мікрофон, зупинка відповіді,
історія. Унизу видно останній обмін репліками в чорних бульбашках:
користувач праворуч, ValleRa ліворуч, джерела поруч із відповіддю.
Кнопка історії розгортає попередні репліки; довгі відповіді прокручуються
без обрізання тексту. Введення залишається під стрічкою. Розмова порожня
до реальних подій сесії — текст зі зразка дизайну не підставляється.
Під час сценарію з'являється картка завдання,
а підтвердження не ховаються разом з історією. Меню «···» містить стан
сесії, паузу діалогу й перемикач пульсації світла.

Обличчя без моргання, руху погляду чи артикуляції. У спокої рот — коротка
рівна фіолетова лінія. Під час мовлення замість неї з'являються дві
світлові хвилі, їхня форма змінюється за аудіосигналом, очі світяться
яскравіше. Світлових дуг та яскравої обводки голови більше немає.
У вебрежимі прямий Windows TTS на типовому пристрої передає PCM16/22050 Hz
у потоковий WinMM-вихід: три буфери максимум, по 2048 байтів (~46 мс).
Після відтворення блока до UI надходять 32 усереднені знакові значення
та RMS-рівень. Контур перебудовується, а не масштабує готову синусоїду;
його ширина — 56 одиниць SVG, у 1,4 раза ширша за рот у спокої (40).
Друга лінія — слабша копія
того самого сигналу. Це згладжений та проріджений сигнал, не осцилограф
і не вимір звуку в кімнаті. Синхронність залежить також від драйвера й UI.
Телеметрія обмежена інтервалом 65 мс, інтерполяція UI — приблизно 30 кадрів/с
лише під час зміни форми. Мікрофон/інші програми не захоплюються, повного
файлу відповіді чекати не потрібно. Нових залежностей чи моделей немає.
Без PCM-даних (WAV/інші рушії/помилка адаптера) рот залишається лінією,
без штучної резервної пульсації. За відсутності кадрів 300 мс ефект згасає.
Завершення/помилка/stop скидають стан; згасають також застарілі події.
Є вимкнення пульсації; прихована вкладка не пульсує. За явним запитом
користувача окремий дозвіл світлових ефектів попри prefers-reduced-motion
увімкнений початково. Його можна зняти в меню «···», щоб дотримуватися
системного зменшення руху. Windows не змінюється, виняток стосується лише
світла обличчя та хвилі рота. Обидва перемикачі зберігаються локально
для адреси UI в цьому браузері, якщо сховище браузера доступне.
У меню «···» є пояснення стану підсвічування та «Перевірити світло · 3 с»:
локальний статичний зразок хвилі на демонстраційних даних без голосу, API й команд. Демонстрація
явно позначена й враховує обидва перемикачі світлових ефектів.
Якщо не працює навіть демонстрація, перевір це пояснення; якщо працює
демонстрація, але не мовлення — перевір підключення/статус TTS.
Адаптер services/audio/speech_pulse.cs компілюється штатним Add-Type тільки
у вебрежимі, раз на TTS-процес. Якщо адаптер недоступний, голос продовжує
працювати зі статичним ротом. Помилка вже розпочатого PCM-відтворення
не повторює частково озвучену фразу; наступна використовує штатний вихід.
18.09 локальна жива проба перевірила коротку/довгу репліку, stop і повторний
запуск: завершення stop — 122 мс, перший завершений PCM-блок прогрітого
рушія — 178 мс. Це не акустичний вимір і не гарантія для іншого обладнання.
У короткій пробі CPU голосового процесу: 19,1% одного ядра штатно,
22,7% із PCM; довга прогріта PCM-проба — 10,1%. Це одиничні заміри без
браузера/STT/LLM, а не навантаження всього асистента. Холодна підготовка
PCM — 665 мс; окрема вартість компіляції не відділена. Див. журнал J35.
Після зміни UI перезапусти ValleRa й відкрий посилання
нової сесії: сервер зчитує ресурси інтерфейсу під час запуску.

- У вебрежимі мікрофон спочатку **вимкнений**. Кнопка вмикає/вимикає
  захоплення на комп'ютері з ValleRa; браузер не записує й не відтворює аудіо.
  При вимкненні незавершена репліка відкидається; UI показує перехідний стан,
  поки поточне захоплення/розпізнавання завершується.
- «Зупинити» перериває лише безінструментальну генерацію та озвучення,
  не скасовує локальні операції. «Пауза» не вимикає мікрофон. Кнопка
  повернення з паузи тільки відновлює діалог, не повторює запит до LLM.
- Кнопка «+» передає звичайну команду нової розмови через чинне підтвердження.
  Підтвердження у вебпанелі прив'язане до конкретного активного запиту.
- Локальні дії, як раніше, починаються зі слова «Команда»; UI не обходить
  маршрутизатор, чергу, перевірки доступу чи підтвердження навичок.
- Закриття вкладки **не вимикає мікрофон і не завершує застосунок**.
  При втраті зв'язку UI не стверджує, що мікрофон вимкнений.

Параметри: `--no-browser` показує лише посилання в терміналі;
`--web-port 8765` задає порт (типово ОС обирає вільний);
`--text-only --web-ui` вимикає голосове введення, але не TTS.
Звичайний `python main.py` зберігає попередній консольний режим.

Сервер слухає **тільки 127.0.0.1**; телефон/інший ПК поки не підтримуються.
Для API потрібен випадковий ключ поточної сесії з посилання у терміналі.
Він передається спочатку у фрагменті URL, потім у заголовку Authorization;
не записується в журнал. Не публікуйте це посилання. Після перезапуску
потрібне нове посилання. Є перевірки Host/Origin, CSP та обмеження запитів;
це не сервер для публічного розгортання і не захист від шкідливого ПЗ на ПК.

Вебвікно тримає останні 200 блоків, сервер — 300 подій поточної сесії.
Збережені приватні історії автоматично не завантажуються в браузер;
наявна історія LLM й журнали застосунку працюють як раніше. Текст діалогу
може надсилатися налаштованому LLM-провайдеру: локальний UI не означає
повністю офлайн-асистента. Паролі/ключі не слід вводити в чат.

Перевірка 17.09.2026: статичний Python/JS-контроль і візуальний перегляд
непідключеної сторінки на широкому/вузькому екрані. Живий наскрізний цикл
API → команда → STT/TTS ще не перевірено. `tester.py` не змінювався й не запускався.
J24 перевіряв початкову двоколонкову версію, J25 — лише статичні перевірки.
Для нового компонування J26 окремо переглянуто непідключений UI при
1280×720 і 390×780, історію, діалог налаштувань і вимкнення міміки.
Синхронність обличчя з живим TTS та навантаження на X250 ще не вимірювалися.

### Перший багатокроковий сценарій

```text
Команда: режим робота
Команда: підготуй робоче місце
Команда: підготуй робоче місце: Chrome, Telegram
Команда: налаштуй робоче місце: браузер, VS Code, Telegram
Команда: статус завдання
Команда: повтори невдалий крок
```

Це обмежений сценарій для Windows, не довільний LLM-планувальник.
Короткий голосовий виклик: **«Команда, режим робота»**. Також підтримуються
«Команда, увімкни режим робота» та «Команда, активуй режим робота».
Це псевдонім запуску збереженого сценарію, не постійний режим і не дозвіл
виконувати подальші репліки без слова «Команда». Підтвердження залишається.
Стара фраза «підготуй робоче місце» теж працює. Новий псевдонім не змінює
STT і поки не перевірений на живому аудіо.
Коротка команда використовує `data/workplace.json`: за вибором користувача
збережені браузер за замовчуванням, VS Code і Telegram. «Браузер» визначається
за асоціацією HTTPS поточного користувача Windows, не підміняється Chrome.
Можна назвати від 1 до 3 програм **через кому** для одного запуску, точними
назвами або налаштованими псевдонімами індексу. Такий список не змінює профіль.
`Налаштуй робоче місце` зберігає новий список лише після підтвердження, без запуску.
Якщо будь-яку назву не визначено однозначно,
нічого не запускається: слід уточнити назву й повторити повну команду.

ValleRa спершу перевіряє весь список, показує план і просить підтвердити
назви та шляхи програм. Повні шляхи відображаються в картці/підтвердженні й
журналі; вголос читаються тільки операція та назви програм. Підтримуються тільки локальні EXE й ярлики на EXE
без аргументів; скрипти, URL, мережеві шляхи та аргументи команд не виконуються.
Перед кожним запуском індекс/шлях/розмір/час зміни файла перевіряються повторно.
Програма запускається без shell і без змін конфігурації/файлів користувача.

Для кожного кроку перевіряється **процес із тим самим шляхом EXE та його видиме
вікно**. Очікування вікна — до 8 секунд. Це не перевірка чуйності інтерфейсу,
входу в акаунт чи завантаження проєкту; вікно може бути згорнутим/перекритим.
Уже виявлений процес повторно не запускається. Якщо він працює лише у треї,
асистент повідомляє, що вікно не підтверджено; сам вікна не розгортає.
Якщо процес або вікно не підтверджені (зокрема через права доступу або launcher),
стан позначається невідомим, решта кроків зупиняється, автоматичного повтору немає.
Успішність не оголошується лише через прийнятий системою запуск.

Скасування: кнопка «Скасувати кроки» в картці або текстова команда
`Команда: скасуй завдання`. Це зупиняє наступні кроки, не закриває програми,
які вже запущені. Кнопка «Зупинити» лишається зупинкою відповіді, не завдання.
Одночасно виконується один сценарій; голосове перебивання під час виконання
не реалізовано. План і його стан не відновлюються після перезапуску.
Перевірки процесів — обмежені за часом; це не транзакційний відкат і не
захист від підміни файлів іншим локальним процесом. Офлайн-поведінкові перевірки
доступні через `tester.py --module commands --filter WorkplaceChecks`.
Читання реального профілю, індексу та вікон без запуску програм:
`tester.py --probe workplace --allow-live --timeout 45`.
Користувацький тест 19.09 (J41) виявив помилки старої голосової фрази та
непідтверджене вікно Telegram. Нову логіку J42 треба перевірити наживо окремо.
Асоціація браузера читається через
[Windows AssocQueryStringW](https://learn.microsoft.com/en-us/windows/win32/api/shlwapi/nf-shlwapi-assocquerystringw)
з [ASSOCF_IS_PROTOCOL](https://learn.microsoft.com/en-us/windows/win32/shell/assocf_str).

### Каталог, наміри та контекст завдання

За `commands.natural_actions: true` (увімкнено) можна сказати «Відкрий Telegram»,
«Підготуй мене до роботи», «Статус завдання», «Повтори невдалий крок».
Один потоковий запит LLM обирає розмову, уточнення або пропозицію дії.
У природному режимі весь короткий пакет відповіді перевіряється до озвучення,
щоб змішаний ACTION/JSON не потрапив у голос. Це додає очікування кінця генерації;
перевірений текст далі озвучується фразами. Пропозиція виконується лише після
перевірки та підтвердження. Статус — лише читання, без дозволу.
Без префікса підтримуються пошук файлів, відкриття програми, погода, вебпошук,
робоче місце, його статус і повтор, розгортання/згортання/відновлення вікна.
Решта можливостей — через точні команди.
Назву програми, параметри пошуку файла або місто можна уточнити наступною
короткою реплікою протягом 120 с. Уточнення обмежене початковим типом завдання;
перед виконанням залишається підтвердження. Новий запит чи прострочення скидають
контекст. Поза конкретним запитом підтвердження або вибору саме «так» не дозволяє дій.
Точна фраза «режим робота» одразу готує локальний план для погодження, без LLM.
Однозначне «Відкрий Telegram», «Запусти VS Code» або «Відкрий браузер» також
може обійти LLM: назва/псевдонім повинні точно відповідати одному запису
локального каталогу (браузер — окремий штатний виконавець). Нечіткі назви,
складні фрази й уточнення залишаються на звичайному маршруті. Каталог читається
з бюджетом 250 мс; помилка/перевищення бюджету повертає звичайний розбір.
Це не автоматичний запуск: підтвердження, перевірка аргументів і результату
збережені. У журналі маршрут позначено `route=local_exact`, час читання —
`command.local_app_lookup`. Швидкий маршрут не потребує доступності API.
Голосові спотворення початкової пари «розгорний/розгорнені викно/вікно»
нормалізуються до «розгорни вікно» до вибору маршруту. Це не довільне fuzzy-
виконання: локальний вибір конкретного вікна й підтвердження збережено;
текстовий ввід та слова всередині розповіді не переписуються.
Перевірена коротка відповідь тепер повністю передається в чергу TTS ще до
завершення службового очищення LLM-запиту/запису історії. Сирі токени ACTION
не озвучуються; перевірка всього пакета залишається. Незмінена відповідь не
перезаписується в історію вдруге. Фактичний виграш до звуку потребує живого заміру.
Мережеві затримки Gemini журналюються окремо як `Gemini request`: час підготовки
клієнта, першого тексту, TCP/TLS та HTTP-заголовків, розміри контексту й доступні
лічильники токенів. Текст запиту, заголовки HTTP та ключі в цей запис не входять.
Очікування HTTP-заголовків охоплює мережу й сервіс, а не лише генерацію моделі.
Перевірка 24.09 (J48) відтворила 24–45 с саме тут навіть без історії; keep-alive
цього не усунув. Заміна на 3.1 Flash-Lite дала 503, 2.5 Flash-Lite — 404;
залишено попередню модель. Локальні правки не гарантують усунення затримок API.
На Windows «розгорни вікно Telegram», «згорни вікно Telegram», «віднови вікно
Telegram» працюють із конкретним наявним вікном. Коротка форма «розгорни вікно»
запитує назву; наступна коротка відповідь уточнює її без нового LLM-запиту.
За кількох збігів потрібно обрати номер. Перед дією — підтвердження, після —
перевірка стану; HWND/PID/час створення процесу/EXE/заголовок перевіряються
повторно, щоб не змінити інше вікно. Передній план перевіряється окремо.
Приховані вікна у треї не запускаються і не відновлюються цим шляхом.
Закриття вікон і завершення процесів до природних намірів не додано.

Початкові голосові «запустив», «розгорне» та службові слова «тепер», «Валера»,
«будь ласка» нормалізуються лише як пропозиція для підтвердження. Розповідь
«я запустив…», заперечення й цитати не стають дозволом. Це не зміна STT-моделі.
Для модельних дій і вікон голосове підтвердження коротке, наприклад
«Відкрити Telegram? Так чи ні»; повні деталі лишаються в UI/лозі.
Відмову або тайм-аут повідомляє один виконавець, без дублювання. Скорочене
погодження робочого місця також не дублює скасування. Старі інші навички
залишають попередній формат підтвердження.
Дані історії/вебсторінок не є дозволом. Консервативний локальний фільтр може
перепитати складне прохання чи фразу з лапками. Це не ідентифікація мовця.
Без API використовуйте «Команда: …». `natural_actions: false` повертає попередній
режим; `llm_interpretation` окремо керує розбором явних команд.
Користувацька сесія 19.09 виявила дефекти змішаного формату й уточнень; після
виправлення потрібен повторний живий тест. Довільне редагування
плану під час підтвердження наразі не підтримується.

`core/command_catalog.py` — спільні приклади можливостей для довідки та LLM,
а також поля/належність навичкам для обмежених агентних намірів. У довідці й
підказках моделі враховуються завантажені навички. Детерміновані обробники
старих команд залишаються в навичках; каталог не є довільним виконавцем.

Після точних команд перевіряються близькі короткі фрази робочого сценарію,
наприклад «Команда, підготуй мене до роботи». Нормалізація не змінює назви
програм чи пошукові параметри; заперечення й зайві дії не виправляються в запуск.
Єдиний кандидат переходить до погодження локального плану, кілька — до уточнення.
Це зіставлення вже розпізнаного тексту, не покращення акустичної моделі.

За ввімкненого `commands.llm_interpretation` складніші фрази можуть стати
лише одним із восьми намірів: пошук файлів, відкриття програми, погода,
вебпошук, збережене робоче місце, його статус або повтор, керування вікном.
Невідомі поля/інструменти відхиляються,
параметри перевіряються локально, перед дією потрібне підтвердження.
Для інших можливостей каталогу збережено точні команди, не розширено права LLM.

Останній результат робочого сценарію зберігається в оперативній пам’яті 5 хвилин.
«Команда, статус завдання» читає його без нового запуску. «Команда, повтори
невдалий крок» складає новий план лише з непідтверджених/пропущених кроків:
повторно визначає програми, перевіряє процеси й запитує новий дозвіл.
Це не автоматичний повтор або гарантія усунення причини збою. Підтверджена нова
розмова/новий сценарій очищує попередній контекст; після рестарту він відсутній.
Стан вікна Telegram у треї та акустичне розпізнавання цією зміною не виправлені.

## Встановлення на Windows

```powershell
py -3.12 -m venv .venv
.venv\Scripts\activate
python install.py
python tools\download_vosk_model.py
python tools\download_whisper_model.py
python main.py --setup
python main.py
```

Мінімальне встановлення для Raspberry Pi без Whisper і desktop-пакетів:

```bash
python install.py --profile raspberry_pi
python tools/download_vosk_model.py
python main.py --setup
python main.py --profile raspberry_pi
```

Додаткові провайдери та computer vision встановлюються окремо:

```powershell
python install.py --with-extra-llm
python install.py --with-vision
```

Для чоловічого українського голосу встановіть RHVoice і голос **Volodymyr**. ValleRa шукає голос за фрагментом назви, указаним у `config.json`.

## Журнал кожної сесії

Кожен запуск `main.py` створює окремий UTF-8 файл у `logs/sessions/`:
`session-ДАТАTЧАСZ-PID-ID.log`. Шлях показується на початку запуску;
файл відкривається до завантаження налаштувань і запиту майстер-пароля.

Службові `[PERF]`, `[STT]`, `[LLM]`, розпізнані репліки, Python-попередження
та traceback більше не засмічують термінал. Вони записуються у журнал разом
із текстовими запитами, відповідями, підтвердженнями й завершенням сесії.
Повідомлення окремого Whisper-процесу надходять у той самий файл через чергу;
запис на диск виконує окремий потік. Термінал показує діалог, результати команд,
підказки, запити пароля та короткі повідомлення про проблеми, що потребують уваги.

**Журнал містить текст розмови.** Приховане введення пароля не записується;
відомі програмі секрети й типові записи облікових даних маскуються, зокрема
в traceback. Це не гарантує розпізнавання будь-якої приватної інформації:
переглядайте файл перед передаванням іншим. Аудіозаписів ця функція не створює.

Старі `logs/valera.log*` не змінюються. Журнали сесій не видаляються автоматично
(`logging.retention_days` належав попередній щоденній ротації); за потреби
архівуйте або видаляйте їх вручну. `data/metrics.jsonl` і команди аналізу
швидкодії залишаються сумісними. При штатному виході та Ctrl+C черга журналу
дозаписується; примусове завершення процесу чи вимкнення живлення може
втратити останні записи. Нативний шум аудіобібліотек, який раніше приглушувався,
не вмикається знову; зовнішні вікна та повідомлення ОС не є частиною журналу.

## Профілі продуктивності

- `balanced` — параметри STT із `config.json`, пріоритет точності;
- `fast` — стандартний профіль для слабших ноутбуків, Whisper `beam_size=1`;
- `raspberry_pi` — Vosk без Whisper, один LLM retry, до 64 хостів і 20
  паралельних мережевих перевірок.

Профіль можна зберегти у `performance.profile` або тимчасово передати через
`--profile`. Тиша не передається Whisper. Моделі, індекс програм, healthcheck
LLM і перевірка оновлень готуються після появи інтерфейсу.

У профілі `fast` короткі відомі привітання, подяки й відповіді («привіт»,
«дякую», «так», «добре» тощо) з впевненістю Vosk від 0.92 не проходять
друге декодування. Складні фрази та команди все ще уточнюються Whisper.
Whisper живе в окремому процесі, який можна припинити під час виходу.

## Режим авторизованого аудиту «Душогуб»

Режим неактивний після запуску й не починає сканування автоматично. Базова
послідовність команд:

```text
Команда: Активуй Душогуб
Так
192.168.1.10
Статус Душогуба
Вимкни Душогуб
```

Вхід у режим підтверджується один раз. Після цього IP-адреса або CIDR запускає
сканування автоматично; адресу можна ввести текстом або продиктувати
українськими числівниками. Quick-профіль використовує вбудований TCP connect
scanner, HTTP probing і обмежений content discovery.
Звіти зберігаються у `data/pentest/<scan-id>/report.json` та `report.md`.
Події дозволу й виконання записуються у `data/pentest/audit.jsonl`.

Режим не експлуатує знайдені вразливості, не обходить автентифікацію та не
виходить за підтверджену ціль. Він формує докази конфігураційних ризиків і
рекомендації з їх усунення.

Один запуск обмежений 256 хостами. Link-local, multicast та unspecified адреси
заблоковані, HTTP redirects не виходять за заданий scope.

## Голосова взаємодія

Після запуску асистент автоматично слухає завершені репліки:

```text
репліка → відповідь ValleRa → автоматичне очікування наступної репліки
```

Vosk швидко визначає межі репліки, після чого локальний Whisper повторно
розпізнає той самий аудіобуфер українською мовою. Контекстна підказка і словник
власних термінів зменшують помилки у словах «Валера», «Команда», «Telegram» і
«Душогуб». Для підтверджень із короткою закритою граматикою залишається Vosk,
тому вони не отримують зайвої затримки. Ім'я «Валера» є звичайною частиною
розмови й не керує мікрофоном.

Діалог покроковий: під час власної TTS-відповіді асистент не розпізнає звук,
щоб не почути самого себе. Щойно відповідь завершилась, мікрофон автоматично
повертається до прослуховування.

Поки програма запущена, мікрофон активний для наступної репліки. Аудіо
розпізнається локально, але отриманий текст звичайної розмови надсилається
активному LLM-провайдеру. `Ctrl+C` завершує програму й прослуховування.
Невпевнена голосова репліка не надсилається LLM: асистент локально просить
повторити її. Поріг звичайної розмови — `stt.chat_confidence_threshold` (0.5),
поріг локальних команд — `stt.command_confidence_threshold` (0.55). Текстове
введення не проходить перевірку впевненості STT. Дочірній Whisper ігнорує
консольний `SIGINT`: Ctrl+C обробляє головний процес, який завершує дочірній.

Gemini передає текст потоково. У звичайному tool-free шляху завершені фрази
одразу надходять TTS; у natural_actions спочатку перевіряється весь пакет.
Windows TTS на стандартному аудіовиході говорить без проміжного WAV, з одним
постійним SAPI-процесом. Якщо вибрано конкретний `output_device`, кожна коротка
фраза синтезується в окремий WAV. Інші LLM-провайдери поки повертають повний
текст, який теж озвучується фразами. Це не full duplex: перебивання голосом
під час TTS ще не підтримується. При обриві LLM-потоку почута частина не
повторюється на резервному провайдері.

### Керування розмовною відповіддю

У звичайному режимі спілкування, без слова «Команда»:

- «Зачекай» / «пауза» — пауза розмови: звичайні репліки не надсилаються
  до LLM, доки не надійде команда керування розмовою. Текстова пауза зупиняє
  поточну генерацію й озвучку; уже розпочаті локальні дії не скасовує.
- «Продовжуй» — вихід із паузи. Якщо генерація була перервана — запит на
  продовження за збереженим текстом; якщо вже завершена — повернення до
  слухання. Поза паузою — продовження пояснення на попередню тему через LLM.
- «Повтори останнє» / «повтори» — повтор збереженої розмовної відповіді без
  нового LLM-запиту. Локальні команди не виконуються повторно.
- «Коротше» / «скажи коротше» — переформулювання останньої розмовної
  відповіді до 1–3 речень; «поясни простіше» / «простішими словами» — спрощення.
  Це один логічний запит до LLM зі звичайною політикою резервування, без інструментів.

Ці фрази керують останньою відповіддю звичайного чату, а не результатами
локальних команд/вебпошуку. Повтор і переформулювання також виводять із паузи.
Кеш існує тільки до завершення сесії або підтвердженої «Команда, нова розмова»:
до 2000 символів питання і 10000 відповіді. Про обрізаний повтор повідомляється.
Це згенерований текст, не точний запис того, що користувач почув; продовження
не означає відтворення з тієї самої аудіопозиції. Звичайна історія LLM і журнали
продовжують зберігатися за наявними правилами.

**Пауза не вимикає мікрофон або журналювання розпізнаного тексту.** Явні
локальні команди й підтвердження залишаються активними. Голос під час TTS,
як і раніше, не слухається: для негайної паузи озвучки використовуйте текст.
Поведінкові/живі тести цієї зміни не запускалися; виконано лише статичні перевірки.

### Погода та пошук

```text
Команда: погода в місті Луцьк
Команда: знайди погоду в Луцьку
Команда: прогноз погоди в місті Луцьк на завтра
Команда: знайди в інтернеті офіційний сайт Raspberry Pi
```

Погода зараз, сьогодні й завтра отримується зі структурованого API wttr.in,
а не з уривків пошуку. Без міста або з непідтримуваним періодом асистент
просить уточнити повну команду. Для Луцька підтримуються відмінки та вузькі
виправлення ASR із тестових логів; довільні назви міст нечітко не вгадуються.

Інформаційний пошук читає до трьох доступних публічних HTML/text-сторінок і
робить один окремий запит до LLM для короткої відповіді з номерами джерел.
Відповідні посилання, час читання та дата публікації (якщо її вказала сторінка)
показуються в консолі. Якщо сторінки недоступні або підсумок не вдався,
Валера прямо повідомляє про це; пошуковий уривок не видається за прочитану сторінку.
Запити на «офіційний сайт», «посилання на» чи «адресу сайту» повертають ресурси
без додаткового читання і модельного запиту. Погода залишається структурованою
локальною командою без генерації LLM.

```text
Команда: знайди в інтернеті чому восени жовтіє листя
Команда: уточни пошук поясни простішими словами
Команда: знайди офіційний сайт Python
```

Уточнення використовує останні прочитані джерела протягом п'яти хвилин і
не оновлює сторінки; Валера це озвучує. Новий пошук або підтверджена нова розмова
очищає цей контекст. Для свіжих даних повторіть повний пошук.

Звичайний діалог також отримує тимчасовий статус останнього пошуку й наявний
підсумок із давністю до п'яти хвилин. Це недовірені дані, не авторитетна локальна
дія; сирі сторінки в історію не додаються. Розмова не запускає пошук сама.
Відбір витягів у межах тих самих 5000 символів враховує слова запиту, а не лише
початок сторінки. Для рецептів і факультетів діють прості перевірки потрібних
деталей; це не універсальний семантичний аналіз чи гарантія повноти відповіді.

Голосові форми «знайдив інтернеті» та «знайдє в інтернеті» виправляються лише
після явного слова «Команда», без переписування назв у самому запиті.
Модельна пропозиція вебпошуку не може додати прикметник, змінити число або
викинути заперечення: при лексичній невідповідності дія не виконується.
Сувора перевірка може відхиляти коректні перефразування; точний локальний
шлях «Команда, знайди в інтернеті <запит>» не потребує модельного розбору.

Читач не запускає JavaScript, не використовує браузерні cookies, проксі,
авторизацію чи локальні файли. Дозволені лише публічні HTTP(S)-адреси на
портах 80/443. DNS перевіряється перед з'єднанням із зафіксованою IP-адресою;
кожне перенаправлення перевіряється знову. Ліміти: три сторінки паралельно,
7 секунд на сторінку з перенаправленнями, до 2 000 000 байтів відповіді
(окремо обмежені передані й розпаковані дані, підтримано gzip) та 5000 символів
видимого тексту на джерело. Інші види стиснення, PDF та сторінки, що потребують
JavaScript/входу, поки не підтримуються.

Ранжування використовує повний доступний уривок пошуку до скорочення
для показу. Заголовки всередині статей зберігаються; навігація відкидається.
У `page_reading.outcomes` є номер кандидата й причина невдалого читання.
HTTP 401/403 означає відмову доступу читачеві, а не відсутність сторінки;
коли жодне джерело не прочитано, відповідь явно пояснює це обмеження.
Короткі сторінки верифікації (включно з HTTP 200) та явний заголовок
challenge класифікуються як `browser_verification` і не надходять до LLM
як джерело. Згадка CAPTCHA у статті чи форма з віджетом сама по собі
не є підставою відхилення. Це евристика, не гарантія виявлення всіх перевірок.

Якщо всі сторінки недоступні або оцінена відповідь неповна, дозволено
не більше одного додаткового пошуку: до 8 с на пошук, до 30 с разом із
читанням і підсумком альтернатив. Для недоступних джерел запит зберігається;
можуть додаватися виключення до трьох відмовлених доменів, якщо користувач
не задав явний `site:`. Для неповної відповіді пріоритет отримують слова
початкового питання, пов'язані з браком даних. Сторінка/LLM не задає нових тем.
Уже спробувані URL, зокрема варіанти з іншим `#фрагментом`, відсіюються.
Рекурсивних повторів немає. Невдала альтернатива не стирає попередню відповідь
і посилання; за ознак верифікації пропонується ручне відкриття сайту.
Валера не запускає браузер автоматично, не проходить CAPTCHA і не отримує
браузерних cookies. Додатковий пошук може збільшити очікування.
Проба `--probe smoke --allow-live -- --read-pages` читає чотири фіксовані
публічні сторінки без LLM, секретів, аудіо чи приватного діалогу. Вона не
перевіряє знаходження сторінки пошуком або якість згенерованого підсумку.

До моделі надходять лише запит і витяги публічних джерел — без діалогу,
локальної пам'яті та секретів. Запит обмежений 12 секундами, без повторів;
ліміт API спільний із розмовою. Текст сторінок позначений недовіреними даними,
а підсумовувач не має інструментів виконання дій. JSON і номери посилань
перевіряються локально. Для Gemini формат задається також через
`application/json` і JSON Schema запиту, з дозволеними номерами джерел.
Звичайний діалог і його потокова відповідь цю схему не використовують.
Валідатор приймає чистий JSON або один повний Markdown-блок JSON;
переноси рядків усередині тексту нормалізуються для озвучування.
Довільний текст навколо JSON, зайві поля, вигадані номери джерел і
небезпечні керівні символи відхиляються, а не «виправляються» здогадками.
Журнал містить етап і код причини (`invalid_json`, `unsupported_citation`,
`text_limit` тощо), кількість символів/джерел, але не повну відповідь API.
Окрема метрика `web.summary_validation` відрізняє успішний HTTP-запит
від прийнятного підсумку. Це не гарантує фактичної істинності тверджень:
джерела можуть помилятися, а модель — неправильно їх витлумачити. Дата читання
не означає актуальності; дата публікації зі сторінки не перевіряється незалежно.

### Єдиний комплексний тестер

Запускайте з кореня проєкту у його віртуальному середовищі:

```powershell
python tester.py                              # меню вибору модулів
python tester.py --list                       # доступні модулі
python tester.py --all                        # увесь набір
python tester.py --module stt llm              # лише розпізнавання та LLM
python tester.py --module commands files       # команди та робота з файлами
python tester.py --module llm --filter timeout # фільтр за іменем тесту
python tester.py --module tester               # самоперевірка тестера
python tester.py --all --failfast --verbose --timeout 300
```

У меню можна вводити назви або номери через пробіл чи кому; `a` — усі модулі,
`0` — вихід. Спільні перевірки кількох модулів виконуються лише один раз.
`--filter` (`-k`) шукає підрядок у повному імені тесту без урахування регістру.
Якщо жодного тесту не знайдено, це не вважається успішною перевіркою.

У терміналі показується підсумок. Кожен запуск створює окрему папку
`logs/tests/<час-UTC-ID>/`: `details.log` містить вивід і причини помилок,
`report.json` — підсумковий машинозчитуваний звіт, тривалість і результати
окремих тестів. `results.json` — внутрішній результат тестового процесу, якщо
він завершив роботу. `--verbose` додає імена всіх тестів у журнал.
Тайм-аут за замовчуванням — 300 секунд на весь запуск; Ctrl+C скасовує його.
Коди завершення: `0` — успіх, `1` — невдалі тести, `2` — помилка запуску або
порожній набір, `124` — тайм-аут, `130` — скасування.

Це автоматизовані регресійні перевірки з підставними відповідями сервісів:
вони не перевіряють живий мікрофон, фактичне звучання голосу, доступність
провайдерів чи реальну швидкість відповіді. Тестер не запитує майстер-пароль
і не завантажує `.env`; ключі та паролі з оточення не передаються тестовому
процесу. Це ізоляція запуску, **не пісочниця для недовіреного коду**.
Живі режими `--probe` не входять у цей набір.

Наявні файли `tests/test_*.py` залишаються внутрішньою бібліотекою перевірок,
а не окремими інструментами запуску. Нові файли автоматично потрапляють у
`--all`; невідомі групам — у `other`. Прив'язка модулів задається в `GROUPS`
файла `tester.py`. Нові центральні перевірки можна також додавати в цьому ж
файлі, як вбудовану самоперевірку `TesterChecks`.

### Живі перевірки та заміри — у тому самому тестері

У меню оберіть потрібну пробу або використайте `--probe`. Важкі заміри та живі
запити запускаються лише з `--allow-live` (у меню — після підтвердження).
Параметри конкретного режиму передавайте після `--`; його довідка доступна
без запуску: `python tester.py --probe smoke -- --help`.

```powershell
python tester.py --probe smoke --allow-live -- --audio
python tester.py --probe tts --allow-live --timeout 100
python tester.py --probe smoke --allow-live -- --stt
python tester.py --probe smoke --allow-live -- --network
python tester.py --probe smoke --allow-live -- --read-pages
python tester.py --probe gemini --allow-live
python tester.py --probe gemini --allow-live --timeout 360 -- --connection-comparison
python tester.py --probe gemini --allow-live -- --web-summary
python tester.py --probe startup --allow-live -- --stt-sample
python tester.py --probe whisper --allow-live --timeout 1800 -- --models base tiny
python tester.py --probe tuning --allow-live --timeout 1800 -- --corpus "logs/whisper-comparison-ID"
python tester.py --probe endpoint --allow-live -- --corpus "logs/whisper-comparison-ID"
python tester.py --probe turn --allow-live -- --corpus "logs/whisper-comparison-ID"
python tester.py --probe performance -- --turns
python tester.py --probe record --allow-live --timeout 1800
python tester.py --probe recorded --allow-live --timeout 900 -- --corpus "logs/voice-corpus/ID"
python tester.py --probe recorded --allow-live --timeout 900 -- --corpus "logs/voice-corpus/ID" --policy-comparison
python tester.py --probe recorded --allow-live --timeout 300 -- --corpus "logs/voice-corpus/ID" --endpoint-comparison
```

`record` відкриває майстер запису 24 фраз; мікрофон працює лише після
натискання кнопки. `recorded` читає підтверджені WAV із цього корпусу,
перевіряє SHA-256 та порівнює повний запис у Vosk/Whisper із чинним
завершенням репліки. Ця проба локальна: без мережі, мікрофона, озвучування
й виконання розпізнаних команд; моделі мають бути вже завантажені.
Для продовження перерваної проби додайте після `--`:
`--resume "logs/recorded-stt-ID.json"`. Завершені виміри сумісного звіту
переносяться в новий файл із посиланням і SHA-256 оригіналу, без повторення.
WER — помилки слів щодо підтвердженого тексту, не відсоток невиконаних команд.

Gemini `--connection-comparison` — максимум 6 живих нейтральних запитів,
витрачає API-квоту, не читає історію діалогу. Порівнює новий клієнт і один
повторно використаний клієнт (keep-alive 60 с), через production streaming
із тестовим транспортом. Інтервал між запитами 5 с, deadline запиту 45 с,
без повторів; при першій помилці/429 проба зупиняється. Зберігає лише таймінги
та дозволені коди помилок, не тіла відповідей, заголовки чи ключі.
Транспортні події вимірює через [HTTPCore trace](https://www.encode.io/httpcore/extensions/#trace).
TCP-час включає резолюцію адреси, очікування заголовків — мережу й сервер;
це не окремий вимір часу генерації на сервері. Результати — `logs/gemini-connections-*.json`.
J38: у короткому прогоні медіана першого тексту 1,584 с (3 нових клієнти)
проти 0,610 с (2 теплих запити). J39: повторне використання тепер увімкнене
у робочому провайдері — один ліниво створений Gemini-клієнт на сесію/event loop,
keep-alive 60 с. Healthcheck/chat/stream/вебпідсумки використовують той самий
клієнт, але власні параметри запиту: healthcheck щонайменше 30 с, генерація
щонайменше 60 с (загальний бюджет менеджера може бути коротшим).
Скасування репліки закриває її потік, не сусідній запит і не спільний клієнт.
На виході закриваються async і sync транспорти; після close нові запити заборонені.
Після 60 с простою або закриття сервером HTTP-пул може встановити з’єднання
заново; це не гарантія постійно відкритого сокета. Нових налаштувань не потрібно,
для застосування змін перезапустіть асистента. Довгі затримки 14–20 с цим не пояснено.

`--endpoint-comparison` порівнює фіксовану й адаптивну паузу на тих самих
записах через production-захоплення з імітацією доставки PCM. Whisper позначено
готовим лише для перевірки цього шляху; його inference не запускається.
`--endpoint-block-ms 100` додатково перевіряє менші блоки кандидата; базовий
варіант бере розмір із конфігурації. Це аудіошкала, не жива затримка.
Прапорець `--allow-live` дозволяє важку локальну пробу, але API/мікрофон тут не використовуються.

Експериментальний `stt.endpoint_adaptive` за замовчуванням **false** і в робочій
конфігурації не ввімкнений. За true короткі стабільні розмовні гіпотези можуть
завершитися після 900 мс тиші; команди, довші репліки та очевидно незавершені
кінцівки зберігають `endpoint_silence_ms`. Це евристика, не розуміння завершеності
думки. Штатне завершення Vosk і граматики підтвердження не змінені.
18.09 перевірка 24 записів дала лише 250 мс виграшу на одній репліці;
кандидат із блоком 100 мс погіршив одну довгу фразу. Робочі 250/1200 мс
залишені без змін (J37). У сесійному логу тепер є технічний `STT endpoint`:
причина native/quiet/timeout, тиха пауза та оцінка затримки обробки останнього
блоку; ці показники не містять тексту й не є акустичним виміром.
Час офлайн-обробки не дорівнює затримці живої розмови. WAV і розпізнаний
текст залишаються приватними; перед публікацією звіт потрібно знеособити.

`--policy-comparison` порівнює Vosk на чинній межі репліки, `legacy` та
`vosk_first` на однаковому PCM; еталон використовується лише для оцінювання,
не для вибору тексту. Розпізнавання Whisper спільне для порівнюваних схем,
тому наведені витрати — суми виміряних компонентів, не живий час відповіді.
Цей режим не підтримує `--resume` і не змінює config.json.

Поле `stt.refinement_policy` у config.json:

- `legacy` — попередній вибір із перевагою Whisper; також значення для старих
  конфігурацій без цього поля.
- `vosk_first` — Vosk із confidence від 0,85 зберігає пріоритет. Звичайна
  впевнена репліка обходиться без Whisper; команди й невпевнені репліки
  уточнюються. Розбіжність рушіїв щодо префікса «Команда» зберігає заборону
  переходу до локального виконання. Пороги двох моделей не порівнюються між собою.

Після порівняння користувацьких записів 16.09 `vosk_first` увімкнено в поточній
локальній конфігурації; загальний default та приклад лишаються `legacy`.
Для відкату встановіть `"refinement_policy": "legacy"` і перезапустіть Валеру.
Пауза завершення, модель Whisper та підтвердження операцій не змінені.

Старі скрипти `test_gemini.py` та тестові/вимірювальні скрипти з `tools/`
видалені як окремі точки запуску. Їхня логіка збережена у внутрішньому пакеті
`testing/probes/`; запускати його файли напряму не потрібно. `tests/` містить
регресійні сценарії без власних точок запуску. CI також використовує `tester.py`.
У `tools/` залишилися лише завантажувачі моделей і відновлення сховища — це
не тестери. Самодіагностика всередині асистента залишається його функцією.

Додаткові режими мають ті самі `details.log` та `report.json` у `logs/tests/`.
Детальні JSONL-заміри й синтетичні WAV-корпуси зберігаються за шляхами,
зазначеними в журналі режиму, щоб ними можна було користуватися повторно.
Наведені `logs/whisper-comparison-ID` — приклади: вкажіть справжню папку,
створену режимом `whisper`. Типовий тайм-аут — 300 секунд; для довгих замірів
його можна збільшити через `--timeout` перед роздільником `--`.

Аудіоперевірки використовують тимчасову синтетичну репліку без мікрофона та
відтворення; це не оцінка точності живого мовлення. `--network` надсилає лише
фіксовані публічні тестові запити (погода Луцька, пошук ресурсу й привітання
Gemini), не історію користувача. API-запит може спожити квоту провайдера.

За замовчуванням використовується Whisper `base` на CPU з квантизацією
`int8`, без текстових підказок (`prompt` і `hotwords` порожні). Профіль `fast`
використовує `beam_size=1`; `cpu_threads=2` — значення за замовчуванням після
порівняння на ThinkPad X250 (2 фізичні ядра). Явне `cpu_threads=0` повертає
автоматичний вибір бібліотеки. У локальному синтетичному тесті цей варіант
показав кращий баланс швидкості й точності; див. [порівняння](docs/WHISPER_COMPARISON.md).
Параметри моделі, beam search, VAD та hotwords зберігаються у секції
`stt.whisper` файла `config.json`. Якщо faster-whisper або модель недоступні,
ValleRa продовжує працювати через Vosk і показує причину в консолі та
самодіагностиці.

Зміна STT-підказок не змінює особистість Валери в LLM або правила команд.
Після зміни `config.json` перезапустіть асистента, щоб завантажити нову модель.

Whisper спочатку використовує повний локальний кеш. Звернення до Hugging Face
потрібне лише якщо файлів моделі бракує. Ваги, конфігурація, токенізатор і
словник перевіряються перед завантаженням у пам'ять; нові ревізії моделі
автоматично на кожному запуску не перевіряються.

Звичайні фрази надходять LLM. Локальна дія повинна починатися словом
`Команда`, наприклад:

```text
Команда: відкрий телеграм
```

Відомі локальні команди виконуються без LLM. Після виконання дії наступна
звичайна фраза знову обробляється як розмова. Після запиту підтвердження
відповідь «так» або «скасувати» приймається без додаткового префікса.

### Керований розбір команд і вибір результату

Увімкнено `commands.llm_interpretation`: якщо звичайний маршрутизатор не
розпізнав явну команду, окремий LLM-запит може запропонувати одну з чотирьох
дій: пошук файла за назвою, відкриття встановленої програми, погоду або
вебпошук. Наприклад: **«Команда: допоможи відшукати документ про диплом»**.
Якість довільних формулювань залежить від моделі; це не загальний планувальник.

Перед виконанням такого трактування ValleRa завжди називає конкретну дію
та параметри й просить підтвердження. JSON моделі не є кодом: зайві поля,
невідомі інструменти, шляхи виконуваних файлів і некоректні значення відхиляються.
Модуль не має інструментів редагування, видалення, оболонки, секретів або
пентесту; вимкнені навички не можна викликати через цей механізм.

Розбір отримує лише поточну команду без префікса та фіксований каталог,
без історії діалогу, вмісту файлів і результатів локального пошуку. Запити
з ознаками секретів не передаються цьому модулю. Для хмарного провайдера
текст команди передається йому; не включайте приватних даних у вільний текст.
Одна спроба, стандартний дедлайн 12 с, без повторів чи автоматичного
переходу до іншої моделі; пауза після 429 спільна зі звичайним діалогом.

Пошук файлів зберігає до п'яти результатів лише в пам'яті сесії:

У робочому `config.json` увімкнено `file_search.all_local_drives: true`:
на Windows під час запуску додаються корені всіх локальних fixed/removable
дисків. `user_directories` залишаються пріоритетними початковими папками та
окремою межею для запису/переміщення/видалення. Пошук і погоджене відкриття
можливі за межами цих папок, але ширший пошук не розширює права зміни файлів.
Новий підключений диск підхоплюється після перезапуску. Загальний default та
`config.example.json` лишають `all_local_drives: false` (явне увімкнення).

Пошук читає назви й метадані, не вміст. Мережеві диски автоматично не додаються;
посилання/junction-каталоги не обходяться, недоступні шляхи пропускаються.
Windows ACL не змінюються, підвищення до адміністратора немає. На інших
платформах залишаються явно задані `user_directories`, а не автоматичний `/`.

`file_search.budget_seconds: 15` — м'який бюджет однієї порції (від 1 до 60).
До п'яти знайдених файлів передаються на вибір. Неповний обхід позначається;
повтор запиту з тією самою назвою/типом протягом 5 хвилин продовжує його.
Інший запит, прострочення чи перезапуск скидає курсор. Кожна порція показує
нові збіги, не глобальне сортування всього диска. Це ще не постійний індекс;
великі дерева можуть потребувати кількох порцій. Пошук не працює у фоні між
запитами; при завершенні застосунку курсор закривається.

```text
Команда: знайди документ про диплом
ValleRa: Знайдено: 1. …; 2. … . Який відкрити?
Другий
```

Номер, «другий», «відкрий другий файл» або «скасувати» приймаються без
нового префікса лише під час цього вибору. Вибір одноразовий, має строк
120 секунд і скидається іншою реплікою. Для голосового вибору діє поріг
впевненості команд. Перед відкриттям повторно перевіряються дозволені
каталоги й існування файла; для недокументних типів є додаткове підтвердження.
Неоднозначна команда відкриття більше не бере перший файл автоматично.
Якщо результат один, Валера питає «Відкрити цей файл?»; «так» відкриває саме
цей результат, «ні» скасовує. За кількох результатів «так» не обирає перший.
Повторна перевірка відхиляє змінений/зниклий файл. Пошук підтримує також PNG,
JPG, JPEG, WebP і BMP; невідомий тип можна не вказувати.
Відкриття файла має статус submitted: Windows прийняла запит, але показ вмісту
конкретного документа не перевірений. Для програм перевіряються процес і
немінімізоване видиме вікно; невідомий результат не спричиняє повторний запуск.
Вибір між знайденими програмами працює аналогічно. «Передано системі» ще
не означає, що потрібне вікно гарантовано відкрилося.

Щоб повернути лише строгий локальний розбір, додайте до `config.json`:

```json
"commands": {"llm_interpretation": false, "interpretation_timeout_seconds": 12}
```

Окремий контекст вибору працює й без LLM. [Подальші етапи асистента](docs/ASSISTANT_ROADMAP.md)
охоплюють змістовний вебпошук, робочі сценарії й голосові перебивання;
ці можливості ще не реалізовані цим етапом.

Щоб отримувати повідомлення про нові релізи, укажіть:

```json
{
  "updates": {
    "check": true,
    "github_repository": "owner/repository"
  }
}
```

## LLM fallback

```text
Gemini → Groq → OpenAI → Anthropic → Ollama → шаблонний режим
```

На старті ValleRa перевіряє всі налаштовані провайдери у фоні. Під час роботи
тимчасові мережеві помилки отримують до трьох спроб у межах загального дедлайну
(кількість залежить від профілю). Потім використовуються налаштовані резервні
провайдери. Ліміт квоти, помилка доступу чи налаштування не спричиняють негайних
повторів на тому самому провайдері.

Після HTTP 429 провайдер переходить у локальну паузу. Використовується довша
вказівка з `Retry-After` / `RetryInfo.retryDelay`; якщо їх немає — 60 секунд.
Репліки під час паузи не надсилаються цьому провайдеру. Таймер не запускає
фонових повторів: після паузи потрібна нова репліка користувача. Налаштовані
резервні провайдери й локальні команди залишаються доступними.
Діагностика розрізняє добову/хвилинну квоту, якщо API надає структурований
`QuotaFailure`. Пауза не гарантує відновлення квоти; початок нової розмови
не скидає паузу. Квота на стороні API не скидається перезапуском асистента.
Gemini SDK має одну HTTP-спробу: повторами керує менеджер, без вкладеного retry.

Невдалий запит не вимикає спілкування до перезапуску: наступна репліка знову
звертається до моделі, якщо вона не перебуває в паузі після 429. Резервний провайдер у разі збою може повернутися до
попереднього. Порожня відповідь або обмеження генерації не означають, що API
недоступний. Для структурно порожнього `STOP` Gemini без ознак блокування або
нетекстового вмісту дозволена одна повторна спроба незміненого запиту, до 10 с
у межах загального бюджету та налаштованої кількості спроб. Інші порожні
відповіді й обмеження генерації не повторюються й не пересилаються іншій моделі.
Обмеження безпеки API не змінюються. [Умови повтору та діагностика](docs/RESPONSE_RELIABILITY.md).

Розмовна інструкція просить 1–2 короткі речення, орієнтовно до 40 слів; на
прохання доступні докладні відповіді. Текст не обрізається примусово. Для
голосових реплік модель отримує позначку про можливі помилки STT і необхідність
уточнити незрозумілий зміст, не вигадуючи причини спотворення.

Журнал помилок генерації зберігає категорію, тип винятку, HTTP-код і код причини
завершення Gemini (`finish_reason` / `prompt_feedback.block_reason`), але не
тіло помилки API, запит або історію діалогу. Уже озвучена частина відповіді не
повторюється після збою потоку.
Код `MAX_TOKENS` у журналі позначено `MAX_OUTPUT`, щоб фільтр секретів не
сприймав назву коду як згадку облікового токена.

Gemini отримує системні правила через `system_instruction`, а репліки —
окремими повідомленнями `user` / `model`. Резюме й локальна пам'ять є
контекстними даними, а не системними інструкціями. `PROHIBITED_CONTENT` означає
обмеження з боку API; сам код не визначає, який фрагмент контексту його спричинив.
Асистент не змінює захисні налаштування і не прибирає історію автоматично.

Щоб явно почати іншу розмову, скажіть **«Команда: нова розмова»** та підтвердьте.
Поточні репліки й резюме спочатку зберігаються в `conversation_archives/`
усередині каталогу даних, потім починається порожній діалог. Архів не додається
до нових запитів. Збережені факти довготривалої пам'яті залишаються; це не команда
видалення особистих даних і не гарантія зняття обмежень API.

Окрема перевірка API без історії та мікрофона:

```powershell
.venv\Scripts\python.exe tester.py --probe gemini --allow-live
```

Вона надсилає дві фіксовані нейтральні репліки, використовує звичайну квоту API
й повертає ненульовий код при помилці; заблоковані запити не повторюються.

Для перевірки саме вебпідсумку додайте `-- --web-summary`: замість двох
реплік буде один запит із синтетичним рецептом. Перевіряються реальний
Gemini, схема відповіді та локальний валідатор; сторінки не завантажуються,
історія й особисті файли не читаються. Це тест формату та інтеграції, не
перевірка якості пошукових джерел. Результат із причиною збою або кількістю
тверджень і тривалістю зберігається в журналі комплексного тестера.

## Безпека

- Будь-який код LLM вимкнений за замовчуванням.
- Перед виконанням коду показуються опис і повний код.
- Кожна небезпечна дія підтверджується окремо.
- Підтвердження діє 15 секунд.
- Команди керування локальними секретами не передаються LLM, а чутливі
  значення маскуються в діагностичному виводі.
- API-ключі вилучаються з оточення процесу після створення LLM-клієнтів і не
  успадковуються дочірніми процесами.
- Голосове збереження паролів заборонене; чутливі значення в консолі маскуються.
- Видалення файлів відбувається через кошик.
- `data` та `cache` приховуються у Windows.
- Дозволений лише один екземпляр програми.
- Повторний `--setup` зливає налаштування, зберігає наявні ключі та створює
  резервну копію конфігурації замість її безумовного перезапису.

Після першого налаштування файл `RECOVERY_KEY.txt` потрібно перенести на
окремий захищений носій і видалити локальну копію. Самодіагностика показує
попередження, доки файл залишається біля програми.
